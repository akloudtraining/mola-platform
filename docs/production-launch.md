## Onboarding changes and verification

A signup-confirmation token can no longer select password reset. Confirmation returns the member to password sign-in; only a recovery callback supplies an in-memory password-update token. Callback tokens and provider errors are removed from browser history. Expired links offer a new request; rapid submissions send one request, and pending fields/mode controls are locked.

After signup, the page now keeps the email in a confirmation-only form and clears password fields. Members can resend confirmation from sign-in or an expired confirmation link. The server fixes the resend type to signup and derives the callback from the Site origin; caller-supplied redirect/type values are ignored. Recovery and resend show sanitized network, service, configuration and rate-limit errors. Account-specific outcomes keep the same generic response, and neither email request creates a session. A failed email request is no longer presented as successful delivery.

Each rename records its old/new names in access history, while historical approval actor names remain frozen. Unauthorized and stale edits are rejected. ## Contribution submission retries

A reproduced route regression returned an earlier USD 150 payment as success when the same form was retried with USD 200. The active D1 route now returns a saved contribution only if its original submitting account and recorded intent match: organization, member, numeric amount, currency, method, payment date, normalized title, reference, notes and selected submission obligation. A different record type cannot reuse the same submission as success. Equivalent amount representations and surrounding title whitespace remain safe retries; caller-supplied actors and timestamps never select the recorded identity.

The comparison runs both at the first saved-record lookup and after the guarded insert. If another request wins the same identifier with conflicting details, the loser receives a conflict rather than success for the winner's payment. Conflicts leave the original row untouched and do not disclose audit account identifiers. A legacy report without an original submitter cannot be inferred to belong to the retrying account. Existing member access and own-contribution checks still run before retry matching.

An exact retry returns the current review status and history while preserving the original recording time and submission cutoff, even after an authorized review, member rename or cutoff correction. The client keeps the original submission identifier and input after an interrupted save, background refresh or conflict; it does not mint a new identifier, replay the request, close the form or announce success on a conflict. Members must inspect recorded details before starting another report.

## Agreement version and acceptance workflow

The owner saves the group’s actual agreement text as a working draft under Agreements & notes. Publishing requires the current organization version, exact saved draft, a title, a group decision reference and explicit acknowledgement. The server freezes the title, text, reference, publisher and timestamp as a new numbered version. Its SHA-256 content reference identifies that exact snapshot; it is not an authenticity signature. Editing the working draft does not modify any published text.

Only an enabled, linked founder can record their own acceptance. The form shows the captured version, requires that member’s name and affirmative consent, and submits the captured content reference. The server sets the actual member, principal, consent and timestamp; caller-supplied actors or other founder IDs are ignored. An unlinked owner cannot accept for others. Duplicate publication/acceptance requests are idempotent, changed payloads and stale versions are rejected, and conflicting writes cannot overwrite another acceptance.

A replacement becomes the current version and starts a fresh acceptance list. Earlier text, entered names and acceptance dates remain retrievable in Version history. Renaming a founder or rebinding their account does not rewrite old receipts; a different principal cannot replace an already recorded acceptance for that founder. Ordinary workspace responses omit private principal IDs, while the owner-only full backup retains the original document JSON and audit identities. Acceptance does not automatically enforce penalties, alter shares, issue units, debit bank accounts or satisfy a later version.

Actual group review and member acceptance remain required. The app records the stated acceptance and does not certify independently verified identity or legal enforceability. The staged PostgreSQL import currently rejects the new agreement record type; its validation and complete agreement operations must be ported before any separate cutover. D1 continues to store and export the complete records.
